# 销量数据源可行性调研

结论先行：**2026-10-30 实测确认，商品销量显示在商品详情的 H5 页面上，已登录和未登录都能看到，不在 PC 网页搜索里。** 能否稳定批量读取还没验证。作者文章没说他用的是哪种方式。

| 项 | 证据 | 结论 |

| 商品分享链接（xhslink.com/m/...）| 2026-10-30 实测：短链跳转到 `https://www.xiaohongshu.com/goods-detail/<商品ID>?xsec_token=...&xsec_source=app_share`；已登录浏览器里页面显示价格 ¥2.99、**"已售5471"**（商品销量，精确整数）、店铺 **"已售 3.8万"**（店铺销量，万为单位的近似值）、粉丝数 1819 | 商品销量是精确整数，店铺销量是近似值，增量只能对单品做精确计算 |
| 销量的数据来源 | 页面加载时发出 `GET mall.xiaohongshu.com/api/store/jpd/edith/detail/h5/toc?version=0.0.5&item_id=<商品ID>`，请求头含 `x-s`、`x-t`（页面脚本生成的签名头）；响应约 17KB 的 JSON，其中商品销量在 `itemAnalysisDataText`（字符串 "已售5471"），店铺销量在 `salesVolume`（字符串 "已售 3.8万"），粉丝数在 `fansAmount` | 页面 HTML 是壳，销量来自这个接口；接口带签名头，用普通 HTTP 客户端直接请求需要自己生成签名，本项目不做；用真实浏览器加载页面则由页面脚本自行完成 |
| 不带 cookie 请求同一页面 | 用 curl 请求一次：HTTP 200，约 8.8KB，仅有页面壳，不含 `已售`，也没有内嵌初始数据 | 无登录态下 HTML 里没有销量，需要执行页面脚本 |
| 全新无登录浏览器会话 + 手机 UA 打开同一短链 | 2026-10-30 实测：页面正常渲染，显示"已售5471"和店铺"已售 3.8万"，顶部有"小红书 App 打开看看"横幅 | **未登录也能看到销量** |
| 链接参数变体（均为全新无登录会话） | 2026-10-30 实测四种链接：只带 `xsec_token`+`xsec_source`、不带任何参数、`xsec_token` 填错误值、只带 `xsec_source`；接口均返回 200，响应长度相同（17375 字节），页面都显示"已售5471"和"已售 3.8万" | 商品详情页**不校验** `xsec_token`，也不依赖分享人的 `appuid`；只需商品 ID，即 `https://www.xiaohongshu.com/goods-detail/<商品ID>`。因此 token 有效期问题对商品页不存在 |
| 轻量连续访问 | 2026-10-30 实测：同一无登录会话连续加载同一商品页 15 次，间隔约 5 秒，共约 2.5 分钟；15 次接口均 200，销量均为 5471，页面无验证提示，单次加载约 0.45 秒（首次和偶发 2 秒） | 低频访问没有触发验证。**不能据此推断 2300 个商品每小时一轮也没问题**，该规模没有测，也不建议在未评估风险前测 |

## 2. 三条候选路径

### A. 手机 App + ADB（作者系统 1 的方式）
- 优点：与真实用户行为一致，作者已验证可用；不涉及接口签名。
- 缺点：慢、单设备串行；控件定位随 App 版本变化；2300 单品每小时一次，粗算每天约 3 万次页面访问，单台设备很可能跑不完。
- 适用：候选采集（低频、一次性）。不适合做高频监控。
- 本机已有 ADB 自动化基础：`~/Yuepeng/github/adb-job-autopilot`，思路是用 UI dump 识别控件，坐标和 OCR 兜底，可参考其设备检测和重试结构。

### B. 网页端或分享链接页（H5）
- 优点：HTTP 请求轻量，适合每小时批量。
- 未知：商品页是否在网页或分享页显示销量，是否需要登录，请求是否带反爬参数。
- 风险：见上，风控明确存在。

### C. 第三方数据平台
- 优点：无需自己维护抓取。
- 缺点：通常收费，粒度多为日级，达不到小时级；无法验证覆盖范围。未调研具体产品。

## 3. 推荐的验证顺序

2026-10-30 更新：步骤 1、2 已完成，结论见第 1 节。商品页只需商品 ID，未登录可见销量，销量来自带签名头的商城接口，因此推荐用真实浏览器（Playwright）加载页面读取，不自己实现签名。下面保留原步骤作参考。

不要先写调度和界面，先做一个 1 小时内能出结论的小实验：

1. **手动确认销量在哪里出现**：在手机 App 和桌面浏览器里分别打开同一个商品链接（含分享短链），记录：
   - 页面上销量显示成什么格式（精确数字、"1000+"、"已售 X 件"）
   - 是否需要登录
   - 分享出来的链接在未登录浏览器里能否看到销量
2. **用浏览器开发者工具观察一次页面加载**（Network 面板），只看：销量数字来自哪个请求，还是直接写在页面 HTML 里。记录请求是否带动态参数。只做观察，不要在这一步写批量脚本。
3. **根据结果走决策树**：

```
分享链接在未登录浏览器能看到销量？
├─ 是 -> 路径 B：低频（先 1 次/小时、10 个商品）验证稳定性，再放量
└─ 否 -> 需要登录态或只在 App 内可见
        ├─ 愿意承担账号风控 -> 路径 B + 登录态，严格限速，使用小号
        └─ 否 -> 路径 A，降低规模（缩小监控池、降低频率，只盯重点商品）
```

4. **用 Excel 手动记 10-20 个商品 7 天**，确认"增量"这个指标本身对选品有帮助，再投入自动化。作者文章第七节也是这个建议。

## 4. 对设计的影响

- 数据源层抽象成统一接口：`fetch_sales(item_url) -> {sales, price, ts, status}`。上层调度、快照、预警不依赖具体抓取方式，路径变化时只替换这一层。
- 快照表记录 `status`（成功、失败、被风控、解析失败），避免把失败记成"销量没变"。
- 请求限速、重试上限、遇到验证码或限流时暂停并告警，而不是静默重试。
- 销量解析要兼容"1000+""1.2万"这类格式，并在表里同时保存原始字符串和解析值。

## 5. 合规和风险提示

- 抓取可能违反平台服务条款，高频请求可能触发验证码、限流乃至账号被封。使用小号并自行承担风险。
- 本项目只讨论读取公开页面可见的销量，不涉及绕过验证码、签名或访问非公开接口。
- 文章作者也提醒：真题、讲义、课程类资料可能涉及版权和平台规则，销量好不代表可以直接售卖。

## 6. 仍未验证的内容

- 高频规模：每小时数千次访问是否触发验证或封 IP。需要从低到高逐步放量，每步观察，遇到验证就停。
- 销量显示格式：已实测 5 个商品（已售5471、6514、7832 为精确值；已售1.8万+、已售12万+ 为取整）和 4 个店铺（3.3万、3.8万、6.8万、14.2万），接口里只有字符串字段，没有原始整数。取整无法靠解析恢复，处理方式和样本表见 `requirements.md` 的 2.3.1。仍不清楚：8000-9999 这个区间是精确值还是已经取整，以及更大数值（几十万以上）的档位。
- 同一商品多次抓取的销量是否有缓存延迟（15 次连续访问数值没变，该商品当时没有新增销量，不能说明实时性）。
- 店铺页的销量、以及"店铺新品"列表的入口地址，还没看。

## 7. 尚未调研的内容

- 小红书官方是否提供面向商家或达人的合法数据接口（千帆、蒲公英等需要相应资质，普通账号不可用）。
- 具体第三方数据平台的覆盖范围、价格和粒度。
- 商品页销量的真实显示规则（是否按区间显示、是否有延迟）。

设备：vivo V2547A，Android 16，屏幕 1260x2772，USB 调试已连接；小红书 9.51.0（`com.xingin.xhs`）；本机有 adb，没有 scrcpy。

| 项 | 结果 | 影响 |
|---|---|---|
| UI dump | `uiautomator dump` 能导出小红书首页控件树（约 116 个节点），文字和 `content-desc` 可读，如"关注""发现""搜索""首页""市集" | 可以用文字和描述定位控件 |
| 资源 ID | 大部分是 `0_resource_name_obfuscated`（已混淆） | 不能依赖 resource-id，要用文字、描述和相对位置 |
| 应用分身 | 手机有 vivo 应用分身，启动时弹出"选择要使用的应用"，要选主应用或"Ⅱ·小红书"；`am start --user 999` 没有绕过这个选择框 | 每次启动都要处理选择框；建议固定用分身，避免影响主账号 |
| 深链接搜索 | `adb shell "am start -a android.intent.action.VIEW -d 'xhsdiscover://search/result?keyword=<URL编码关键词>' -p com.xingin.xhs"` 能直接打开搜索结果页（先弹出分身选择框，点选分身后进入），2026-10-30 实测搜"教师资格证真题"成功 | **不需要 ADB 输入法和中文输入**，关键词搜索可以一步到位 |
| 搜索结果页标签 | 全部、用户、**商品**、图片、视频，以及问点点；商品标签内有排序和筛选：综合、销量、店铺、直播、价格升序 | 这就是 PC 网页搜索里缺少的"商品"入口，可以按销量排序 |
| 商品列表可读字段 | 每张卡片有：标题、价格、`已售N`（精确，如 `¥2.99已售5480`、`券后¥1.99已售3551`）、店铺名、店铺销量（`销量3万+`、`销量1万+`）、加购人数（`1000+人加购`）、好评率。列表里**没有商品 ID** | 列表页就能读到销量，但入池需要商品 ID |
| 商品 ID 怎么取 | 点开商品详情页后，`adb shell dumpsys activity activities` 里该 Activity 的 Intent 带 `dat=xhsdiscover://goods_detail/<24位商品ID>?...`，可用正则 `goods_detail/([0-9a-f]{24})` 提取；详情页也能读到精确销量、近 30 天好评、评价数 | **不需要点分享、不需要剪贴板**，点开商品后直接读出 ID，再返回 |
| 与网页销量对比 | 同一商品网页早先显示已售5471，App 列表和详情页显示已售5480 | 两者一致（销量随时间增长），系统 2 用网页读销量是可行的 |
| 文字定位 | 列表里的价格和销量文字同时出现在 text 和 content-desc 里，详情页有“分享商品”“返回”等描述 | 可以用文字和描述定位，不依赖被混淆的 resource-id |
| 未做的验证 | 列表滑动翻页的稳定性和加载等待、“店铺”标签、整店商品列表的入口、连续采集时是否触发验证 | 影响系统 1 的采集规模和节奏 |
| 屏幕锁 | 调研过程中手机锁屏（"双指上滑即可解锁设备"） | 需要手机保持亮屏并解锁，建议开发者选项里开"充电时保持唤醒"；不应自动解锁密码 |
| 账号状态 | 分身首页出现提示"发布失败，已保存至草稿""因违反社区规范禁止发笔记" | 该账号发布功能受限；自动化操作该账号要更谨慎，建议换小号 |
